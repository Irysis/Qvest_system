## 2. 측정 서버 `measure_server.R`

**API(서명 고정)**: `ms_submit(specs, workers = NULL, out_root = NULL)` → 칸별 data.frame(code · ok · status · rc · grade · result · artifacts · log · seconds · worker · attempts · data_version · memo_axis).

**설계**

- 장수 워커(`Rscript --no-environ measure_server.R --worker`)가 칸 큐를 원자적 rename 으로 집는다. 칸마다 정본 셀 워커 `rf_cell_worker.R` 을 **그 파일 그대로** 평가하고, 셀 워커가 `run_paper_replication` 을 그대로 부른다.
- **칸마다 새 프로세스와 같은 출발 상태**를 만든다. 전역 환경을 비우고, 옵션 · 환경변수 · 작업 디렉터리 · 로캘 · 부착 패키지 · 난수 · 그래픽 장치 · 싱크 · 임시 파일을 기준선으로 되돌린다.
  - 셀 워커가 칸마다 run_paper_replication.R 을 다시 source 하므로 코드 상태도 새 프로세스와 같다.
- 새 프로세스와 다른 것은 넷이다. 모두 결과 동일로 실증했다.
  1. `load_rawdata()` 가 메모리 판본 스냅샷의 사본을 돌려준다.
     - 스냅샷은 정수 키로 압축한다: 문자 열 = 코드 + 수준, 0/1 표식 · Date = 정수. 2.22GB → 1.58GB.
     - 기동 때 한 번 풀어 원형과 identical 인지 본 뒤에만 압축본을 쓴다. 꺼내는 데 0.8초 걸린다.
  2. 측정 축 위생 멤버십을 재사용한다. 같은 판본 · 같은 epoch · 같은 계약 파일 md5 이고, 갓 내준 사본일 때만이다. 원 함수의 전역 부수효과는 재현한다.
  3. 정적 PIT 검사 결과를 재사용한다. 키 = 대상 md5 · 검출기 md5 · 가용시점 규칙 md5 · 코드 나무 지문.
  4. R 기동 · 이름공간 · Rcpp 적재를 워커당 한 번만 한다.
- **판본 지문**: 스냅샷을 잡기 전 리프레시 배리어를 본다. 적재 전후 md5 가 같아야 한다.
  - 지문은 칸 산출물 사이드카 `measure_server.json` · 칸 완료 기록 · 배치 요약 `ms_batch.json` 에 남는다.
  - 배치 안 모든 칸이 같은 판본을 쓴다.
- **안전장치**
  - **스냅샷 파수꾼**: 고정 격자 표본 4,096행의 모든 열과 벤치를 기동 때 적어 둔다. 칸을 집기 전 · 사본을 내주기 전마다 대조한다.
    - 어긋나면 그 워커는 칸을 더 받지 않고 끝난다. 새 워커가 새 스냅샷으로 잇는다(fail-closed).
  - 죽은 워커의 칸은 1회 재큐한다(그래도 실패면 `worker_died`).
  - 배리어가 잡혀 있으면 전 칸 `init_failed:refresh_lock` 이다(fail-closed).
  - 사양 md5 가 사전등록과 다르면 측정하지 않는다(R2).
  - 결과가 이미 ok 면 건너뛴다.

**보이는 차이**(측정 경로에 소비자 없음을 grep 으로 확인했다)

- search path 에 `ms:hooks`(commandArgs · quit · q · source · sys.source 갈고리)가 붙는다.
- 칸 출력 싱크가 1개다(`sink.number()` = 1).

**결과 동일 실증**

- 같은 3칸(C0 · C1 추세 현금 오버레이 · C4 팩터 DB 틸트)을 세 가지로 쟀다: 새 프로세스 · 서버 순서 C0→C1→C4 · 서버 역순.
- 6/6 쌍 모두 파일 전부 동일했다(27 · 18 · 27 파일).
- 대조기 양성 대조: 다른 칸끼리는 다르다고 잡는다.
- **순서 대조가 잡은 누수(압축 판 · 10-20)**
  - 압축 스냅샷을 처음 켠 판(E4 · 순서 C4→C0→C1)에서 첫 칸은 같았고, 둘째 칸부터 보유 · 수익 · NAV 가 달라졌다.

  - 수리: 원형 열은 깊은 사본으로 꺼낸다. 위 스냅샷 파수꾼을 함께 넣었다.

**실제 칸 대조**: 핫패스를 적용한 서버(요인 분석 켬/끔 · 압축 스냅샷)와 새 프로세스를 기준선(수정 전 코드) 산출물과 비교했다. 10/10 쌍에서 파일 전부 동일했다(§4).

**`mc_load_raw` 의 mmap 수정 이유(10-20 실측)**

- Windows 에서 col_select + mmap 기본으로 read_parquet 하면, 객체를 지우고 gc 해도 그 프로세스가 끝날 때까지 파일 매핑이 남는다.
- 그 동안 다른 프로세스가 RAWDATA.parquet 를 덮어쓰지 못한다(1224). 구판도 같다.
- 같은 바이트 · 같은 표다.

**채택하지 않은 것**

- `load_rawdata` 의 무복사 적재(setDT)와 열 투영
  - arrow 는 숫자 · 문자 열을 ALTREP(Arrow 버퍼 래퍼)로 돌려준다. 그래서 setDT 는 복사를 뒤로 미룰 뿐이고, 뒤에서 물질화하며 Arrow 버퍼를 함께 쥘 수 있다. 실측 이득은 1.6초에 그쳤다.
  - 열 투영은 러너가 엔진이 쓸 열(기저 엔진 · names() 분기)을 모르므로 적용할 수 없다.
  - 적재 비용은 서버 스냅샷이 없앤다(12초 → 0.6초).

## 5. 남은 병목 · 다음

- **시뮬레이션(10초)**: 리밸런스마다 `dcast` · `Return.portfolio` 를 한다. 행렬 한 번 만들기 + 창 색인이 다음 후보다(핀 파일).
- **엔진 신호(8초)**: 1,416만 행 전체에 setorder · 종목별 shift · frollmean 을 한다. 칸이 바뀌어도 같은 특징(유동성 t−1 · 모멘텀)이다.
- **정적 PIT 검사 첫 스캔(10초)**: `.la_c11_refs` 의 긴 문자열 regmatches 가 비선형이다.
  - 서버는 워커당 1회로 줄였다. 새 프로세스 경로는 파일 수정이 필요하다(비핀).
- **병렬**: 칸 작업 집합(≈6GB)이 묶는다.
  - 2단계(Arrow IPC mmap 공유)는 스냅샷 1.6GB 만 덜어 준다.
